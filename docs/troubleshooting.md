# Troubleshooting

| Symptom | Likely cause | What to do |
|---|---|---|
| `qfn up` or `launch.sh --prod`: "this build has no published image" | This build was released without a prebuilt image (`PROD_IMAGE` is not in `recipe/pins.env`) | Use the dev path: `./recipe/qfn dev` (or `build.sh`, then `launch.sh`) |
| `pull.sh`: "signature check FAILED" | The image at that digest is not signed by the key in `recipe/cosign.pub`, or the checkout's `cosign.pub` was changed | Do not run it. `git status recipe/cosign.pub` should be clean; report it on the forum thread. The dev path rebuilds the same serving code from source |
| `cosign verify-attestation --type spdxjson` on the image: "none of the attestations matched the predicate type: spdxjson" (cosign v3) or a transparency-log error | The SBOM attestation is signed and timestamped but not entered in the public transparency log; only the image signature is | Add `--insecure-ignore-tlog --use-signed-timestamps`, with `--key recipe/cosign.pub` (README, prod path) |
| `pull.sh`: "cosign is not installed" | The signature is not checked without cosign | Install cosign to check it, or use the dev path; the digest pin still guarantees the bytes match what was published |
| `launch.sh --prod`: "not pulled" or "not the build this recipe measured" | The image was not pulled, or something else is under that name | `./recipe/pull.sh` |
| `build.sh`: `manifest unknown` on the base image | Docker Hub pruned the nightly tag | Use the newest build in the CHANGELOG, or the source-build fallback in the README |
| `build.sh`: a patch does not apply | The base is not the pinned commit, or the patch was edited | Use the pinned digest; `sha256sum -c recipe/patches.sha256` must pass |
| `FileNotFoundError: /hfrepo/snapshots/.../model-00001-of-00010.safetensors`, or `launch.sh` reports a file "outside" the model folder | The container mounts only the model folder (`models--nvidia--Qwen3.8-Flash-Next-NVFP4`); its snapshot files are links into `blobs/`, and a link that leaves the folder (a cache moved to another disk behind a symlink) does not resolve in the container. Or `HF_HUB_CACHE` points elsewhere | Keep `snapshots/` and `blobs/` under one folder and run `MODEL_DIR=/path/to/models--nvidia--Qwen3.8-Flash-Next-NVFP4 ./launch.sh`; `launch.sh` honors `HF_HUB_CACHE` and checks every file before it starts |
| Container exits during load, `out of memory` / killed | Not enough free memory at start | Stop other GPU and memory-heavy work; check `free -g` shows about 100 GiB available (`launch.sh` refuses below 98 GiB, `MIN_FREE_GIB`, and lists other GPU containers and processes); see docs/memory-budget.md |
| `ValueError: To serve at least one request with the model's max seq len (262144), (4.32 GiB KV cache is needed, which is larger than the available KV cache memory (N GiB)` | Less memory was left for the KV cache after the load than on our Spark (about 15-16 GiB there): another process grew during the load, or the launch differs from the recipe | One user's Spark stopped showing this error after the NVIDIA driver was reinstalled. Look for `memwatch:` warnings in the log (each names a process that grew during the load, or one that holds GPU memory; its summary gives the server's own peak). Run `./recipe/diagnose.sh` on the saved log (`WARMUP=0 ./recipe/launch.sh 2>&1 \| tee -i launch.log; ./recipe/diagnose.sh launch.log`) and post it. To start anyway with a shorter maximum context: `./recipe/launch.sh -- --max-model-len 131072` (the log's "estimated maximum model length" is the most that fits) |
| Ctrl-C does nothing for a minute or two | During the weight load, vLLM handles the interrupt only when the load ends | `./recipe/stop.sh` from another terminal stops and removes the container at once |
| Load is slower than about 5-6 minutes from a cold page cache | The disk's read-ahead may be the distro default, 128 KB (on earlier builds, 8192 KB took a cold load from about 12 to about 10 minutes; this build's faster loader has not been measured at both settings) | `sudo sh -c 'echo 8192 > /sys/block/nvme0n1/queue/read_ahead_kb'` (use the device `preflight.sh` names). It resets at reboot; to keep it, add a udev rule: `ACTION=="add\|change", KERNEL=="nvme0n1", ATTR{queue/read_ahead_kb}="8192"` in `/etc/udev/rules.d/60-read-ahead.rules`. It changes only the load; decode speed is the same at either setting |
| Load takes much longer than 10 minutes | Slow or busy disk under the Hugging Face cache, other work holding CPU, or `QWEN38_BATCHED_LOAD=0` (patch 0014 off: the weight load then runs on one CPU core and takes about 450-540 s) | Keep the checkpoint on local NVMe and leave `QWEN38_BATCHED_LOAD` unset |
| The load log prints `Attempted to load weight ...A_log with dtype torch.bfloat16 into parameter with dtype torch.float32` (37 lines) | The checkpoint stores 36 `A_log` tensors and one PLE scale in BF16; vLLM keeps them in FP32. Widening BF16 to FP32 is exact | Harmless. Builds before 2026-10-14 print it on every load; this build's patch 0007 removes it, so seeing it means an older build is running |
| The load log prints `Unknown vLLM environment variable detected: VLLM_PLE_CPU_OFFLOAD` or `VLLM_PLE_FILE_GATHER_WORKERS` | Builds before 2026-10-14 set `VLLM_PLE_CPU_OFFLOAD` and read `VLLM_PLE_FILE_GATHER_WORKERS`, which vLLM did not list | Harmless. This build no longer sets `VLLM_PLE_CPU_OFFLOAD`, and its patch 0007 registers `VLLM_PLE_FILE_GATHER_WORKERS`; if you see either line, an older build or a modified `serve.env` is running |
| Other warnings at load: `mamba_ssm_dtype='float32' ... 'bfloat16' was passed`, `max_num_scheduled_tokens is set to 4096`, `num_speculative_tokens > 1 will run multiple times`, `does not support external multimodal embeddings` | Deliberate settings of this recipe (BF16 recurrent state, a 4,096-token step, up to 6 draft tokens, text-only drafting) that vLLM reports on every boot; also `Default vLLM sampling parameters have been overridden by the model's generation_config.json` (the model's own sampling defaults) and `The chat template requires system-first ordering` (inline system messages in /v1/messages are moved to the front) | Expected; the measured numbers use them |
| `launch.sh`: `could not copy recipe/draft-token-maps/<sha256>.json into ...` | A build with a sparse draft head needs its token map in `CACHE_DIR` (default `~/.cache/qwen38-next-dgx-recipe`, mounted at `/root/.cache`). The container runs as root, so earlier runs can leave root-owned folders there that your user cannot write | Run one of the two commands `launch.sh` prints: `sudo install -D -m 0644 <map> <cache path>` copies just the map; `sudo chown -R $USER <folder>` gives the folder back. Then run `launch.sh` again |
| `launch.sh`: the draft token map `is missing` or `does not hash to its name` | `recipe/draft-token-maps/` was not checked out in full, or the file was edited | `git checkout recipe/draft-token-maps` (or a fresh clone); `preflight.sh` checks it too |
| `verify.sh` fails with fluent but wrong answers | The PLE tables are read without their FP8 scale (a broken or different build) | Rebuild from the pinned base and patches; do not mix images |
| `verify.sh` cannot connect | Still loading, or bound elsewhere | `docker logs -f qwen38-flash-next`; check `BIND`/`PORT` |
| HTTP 400 when setting `reasoning_effort` | The chat template accepts only `low`, `medium`, `xhigh` | Use one of those values |
| Slower than the results table | Other load on the box, thinking on, non-English text (the drafter proposes from a reduced token set), or a different driver | Compare with `./recipe/launch.sh --print` and the pins; report with the issue template |

Reporting a reproduction or a problem: run `./recipe/diagnose.sh` (add a saved server log if the start failed:
`WARMUP=0 ./recipe/launch.sh 2>&1 | tee -i launch.log; ./recipe/diagnose.sh launch.log`) and paste its report into
your forum post, or let `./recipe/diagnose.sh --issue` file it on GitHub (it asks first), or open an issue with the
[reproduction report template](../.github/ISSUE_TEMPLATE/reproduction-report.md).
